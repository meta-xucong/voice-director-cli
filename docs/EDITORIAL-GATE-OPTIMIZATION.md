# Narration editorial gate optimization

## Problem and evidence

Before this change, the source-to-script, integrated-pipeline, and rewrite skills required only a main-harness spoken-delivery review, one bounded polish, refreshed source mapping, and independent review. Those requirements were prompt-level guidance only. A clean narration could be handed downstream without a machine-checkable record that those stages happened or that their findings referred to the exact text being handed off. The first Codex Chapter 1 draft exposed this gap: its Markdown contains spoken copy and editorial notes, but no recorded harness assessment/revision or hash-bound independent review.

## Goal

Make the clean narration handoff fail closed unless the private run bundle contains complete, version-bound evidence of (a) one or more main-harness assessment/revision rounds, with the latest self-evaluation passing, and (b) an independent source-fidelity review passing against the same final narration, source evidence, and source map. If a self-evaluation or independent review identifies a concrete issue, revise the draft, reassess it, and repeat review until the final version passes. Do not impose an arbitrary iteration limit.

## Constraints and non-goals

- Keep the existing Voice Director validation, compilation, chunking, and alignment behavior compatible.
- Add one deterministic, offline release gate only. It validates evidence structure, role declarations, hash continuity, statuses, safe output paths, and exact-byte release; it does not think, score prose, rewrite text, call a model/provider, or prove that an attestation is truthful.
- Semantic quality remains a responsibility of the main harness and a distinct read-only reviewer. Never describe a CLI pass as proof that reasoning, oral quality, or source fidelity is true.
- Keep all user source material, narration, source maps, and review reports outside the public repository. No TTS, cloud transfer, publication, commit, or push is part of this change.
- Preserve user-authorized adaptation of examples for the Chapter 1 test while retaining their teaching function. Honor the separate exclusion of “Codex橙皮书”.
- When a review cannot establish a source or interpretation, show the exact uncertainty to the user and record their explicit disposition. Never infer approval from silence.

## Proposed workflow

`source evidence + complete source map -> immutable draft -> main-harness review/revision loop -> candidate self-evaluation PASS -> independent review of exact candidate -> editorial-gate release -> existing voice workflow`

Each harness round records the exact input and output SHA-256, a concise assessment of speakability and listener obstacles, concrete edits and reasons (or an explicit no-change reason), and a post-edit self-evaluation. A self-evaluation of `NEEDS_REVISION` must identify finding IDs; the next round must address those IDs and explain how. Wording findings require changed candidate bytes and a refreshed source map. An evidence-only finding may be resolved with unchanged narration only when the map bytes change, the repair is explained, and a fresh independent review checks that map. Open findings may continue across additional bounded rounds. Any further text change invalidates downstream approvals. The user-requested “continue until ready” behavior replaces the previous exactly-one-pass limit; each pass remains bounded to concrete listener problems and must preserve mapped source meaning and useful content. There is no arbitrary iteration cap; stop only for a true missing source/decision or a repeated finding with no evidence-producing progress, and surface that blocker.

The implementation updates `skills/source-to-script/SKILL.md`, `skills/courseware-pipeline/SKILL.md`, and `skills/humanized-source-rewrite/SKILL.md` to replace the one-pass limit with the iterative review contract and make this command a required release handoff for every new source-to-script run. It also updates `docs/PIPELINE.md`, README, `INTEGRATION_CONTRACT.md`, and `INTEGRATION_PLAN.md` accordingly. An existing direct `validate` or `compile` invocation remains backward compatible, but it is not a narration-release signal. The production workflow must pass only `release/narration.txt` to TTS and downstream work. This is a workflow-level gate; it cannot prevent a person or unrelated tool from copying an unreleased candidate elsewhere.

## Private input bundle and evidence

`voice-director editorial-gate --bundle <private-run-directory> --out <new-release-directory>` reads a fixed bundle:

- `source-evidence.txt`: the reviewed source text/evidence.
- `source-map.csv`: complete source-item map with dispositions and candidate paragraph references.
- `source-maps/<sha256>.csv` (optional): immutable prior map snapshots. Every map hash referenced by a review round must resolve to the current map or one of these files, whose filename equals its exact-byte hash.
- `draft.txt`: immutable first narration draft.
- `candidate.txt`: current polished clean copy; spoken words only.
- `harness-review.json`: harness identity declaration, source/map hashes, ordered rounds, each round's input/output hashes, strengths, weaknesses/listener issues, edits and reasons, addressed and resolved finding IDs, no-change rationale where applicable, and self-evaluation rubric/status.
- `independent-review.json`: distinct reviewer identity declaration; an ordered review history bound per review to exact source, map, and candidate hashes, with explicit finding-resolution IDs; separate extraction coverage, source-item coverage, factual/attribution integrity, spoken delivery, clean-copy readiness, and unresolved-uncertainty verdicts with evidence and finding IDs.

The independent reviewer must be distinct from the declared harness identity. These fields prove only that the package makes distinct-role claims; they are not runtime identity or model provenance.

Schema version 1 is strict: unknown or missing object keys and duplicate JSON keys are errors. Hashes are lowercase SHA-256 of exact file bytes. `harness-review.json` has top-level keys `schema_version`, `harness_id`, `source_sha256`, `map_sha256`, and `rounds`. Each round has `round_id`, `trigger` (`{"type":"initial"}`, `{"type":"harness"}`, or `{"type":"independent","review_id":"..."}`), `source_sha256`, `map_sha256`, `input_sha256`, `output_sha256`, `assessment` (`strengths` and `issues` with `id` and `description`), `edits` (each with `finding_id`, `change`, `reason`), `addressed_finding_ids`, `resolved_finding_ids`, `no_change_reason`, and `self_evaluation` (`status`, non-empty `dimensions` evidence object, and open `findings`). When edits are empty, the round must give a no-change reason and keep input/output hashes identical; wording edits must change bytes and change the source-map hash from the previous round. A map-only finding response must keep candidate bytes identical but change the source-map hash. The first input hash matches `draft.txt`; each later input equals the preceding output; the final output and map hash match `candidate.txt` and `source-map.csv`. A prior `NEEDS_REVISION` requires all open wording-finding IDs in the next round's addressed list and edits; an evidence-only map finding is addressed by the documented map-only path. A finding may remain open across rounds, but must remain visible in self-evaluation or assessment until explicitly resolved; `PASS` requires no open self-evaluation findings.

`independent-review.json` has top-level keys `schema_version`, `reviewer_id`, `source_sha256`, `map_sha256`, and `reviews`. Each review has `review_id`, `source_sha256`, `map_sha256`, `candidate_sha256`, `verdicts`, `evidence`, `findings`, and `resolves_finding_ids`. Schema v2 adds an optional `uncertainties` array to an individual review; use it for the final review when one or more dimensions are `INSUFFICIENT_EVIDENCE`. A v2 document may retain earlier v1-shaped reviews as history. Each review's source hash must match the supplied evidence; its map hash must match the retained map snapshot and harness round that produced its reviewed candidate. Both verdict/evidence objects contain exactly `extraction_coverage`, `source_item_coverage`, `factual_attribution_integrity`, `spoken_delivery`, `clean_copy_readiness`, and `unresolved_uncertainty`; evidence values are non-empty. Verdict values are `PASS`, `NEEDS_REVISION`, or `INSUFFICIENT_EVIDENCE`. A failed review must be followed by a harness round triggered by its review ID, which consumes that reviewed candidate and records every finding as addressed. A fresh review must then cover changed candidate bytes, unless the finding is evidence-only and the source map changed; in that case the candidate may stay byte-identical while the review binds the refreshed map. Findings may remain open through multiple revisions; a later passing review explicitly lists prior issue IDs in `resolves_finding_ids`. For a human-reviewable final result, all non-passing dimensions must be `INSUFFICIENT_EVIDENCE`, spoken delivery and clean-copy readiness must pass, every insufficiency finding must map to a typed uncertainty, and no prior revision finding may remain open.

## Gate behavior

Before writing any output, the gate checks strict JSON shape and values; non-empty evidence; the first input hash matching `draft.txt`; round-to-round hash continuity; last output matching `candidate.txt`; at least one documented harness round; a final self-evaluation of `PASS` with no open findings; all prior findings addressed and either resolved or carried forward; and a final independent review with all six verdicts `PASS`, distinct declared roles, and hashes matching the current source evidence, source map, and candidate. Every earlier non-passing independent review must be followed by a harness round that addresses its findings and a fresh later review that explicitly resolves them. The gate enforces linkage and requires changed candidate bytes for wording edits; an evidence-only repair may keep narration unchanged if it refreshes the source map. The gate does not decide semantic adequacy of a claimed resolution. Any unresolved final blocker, stale hash, missing artifact, or same-role review blocks release.

On success, the gate creates a previously nonexistent output directory atomically, copies `candidate.txt` byte-for-byte to `narration.txt`, and writes `receipt.json` containing the input and output hashes, terminal verdicts, iteration count, tool version, and the scope/limits of deterministic checks. It never modifies its inputs. Failure must leave no partial release directory. It must reject output/input path aliases and existing targets.

Downstream TTS preparation must consume only the released `narration.txt` and receipt, never `draft.txt` or `candidate.txt`. The source-to-script and courseware-pipeline skills must route through this gate; do not describe an ordinary voice CLI `validate` or `compile` pass as satisfying it. The release receipt remains a process-package check, not a semantic quality certificate.

## Test and acceptance plan

1. Write deterministic offline tests for valid release; missing/empty review; malformed or duplicate-key JSON; wrong reviewer/harness identity; first/next/final hash mismatch; failed final self-evaluation; unresolved self-review findings; non-passing independent-review findings with and without a resolving round, including evidence-only map repair with unchanged narration; each failed independent verdict; stale source/map/candidate; invalid UTF-8; output collision/alias/hardlink; and atomic no-partial-output behavior.
2. Prove all existing CLI behavior and tests remain unchanged.
3. With the actual Feishu Chapter 1 source, first run the legacy draft through the gate and confirm it is blocked for missing evidence. Then the main harness performs a real oral-delivery thinking round and edits the script; self-evaluate and repeat bounded revision if any listener-facing issue remains. Refresh the source map. A separate read-only reviewer audits the exact frozen candidate and source. Release only when both reviews pass.
4. Mutate the approved candidate or source map by one byte and verify the prior review can no longer release it.
5. Independently audit the frozen code diff, tests, and required workflow/documentation updates. Any `FAIL` finding receives a bounded fix and a new audit of the new revision.

## Known limits

The gate can detect absent or stale evidence, not dishonest or shallow model-authored evidence. It cannot automatically decide whether a spoken line is natural, whether all source content survived, or whether the user has publication rights. Those judgments must be made by the named workflow roles and reported separately. Runtime model/effort provenance remains unverified unless Codex supplies independent metadata.

## Human uncertainty review

When the final independent review has typed uncertainties and every non-passing verdict is `INSUFFICIENT_EVIDENCE`, `editorial-gate` returns exit code 3 with status `AWAITING_HUMAN`. Its JSON output displays the exact source and candidate references, observed evidence, question, impact, recommendation, available decisions and their effects, and a blank decision template. It does not create a release or modify the bundle. Schema-v1 passing bundles keep their existing behavior; schema-v1 failures do not receive this path.

The final typed schema-v2 independent review contains `uncertainties`, an array that is empty when none exist. Each item has exactly `id`, `finding_ids`, `dimensions`, `source_reference`, `candidate_reference`, `observed_evidence`, `question`, `impact`, and `recommendation`. Every item refers to one or more findings and one or more `INSUFFICIENT_EVIDENCE` dimensions; all findings and all such dimensions must be represented exactly. Historical schema-v1-shaped reviews in the same v2 document may omit this field.

The user may fill the emitted template as a private `human-decisions.json`. Its top-level fields are `schema_version`, `review_id`, `source_sha256`, `map_sha256`, `candidate_sha256`, `independent_review_sha256`, and `decisions`. Every decision contains `uncertainty_id`, `decision`, `user_response`, `user_response_reference`, `decided_by`, and ISO-8601 `decided_at`. The decision file must bind the exact source, map, candidate, and review bytes, and include exactly one decision per displayed uncertainty.

Run the same gate with `--decisions <human-decisions.json>`. `accept_as_is` releases with `RELEASED_WITH_HUMAN_DECISIONS`; the receipt preserves the original independent verdicts, lists accepted uncertainty IDs, and includes the decisions-file hash. It does not rewrite a reviewer verdict to `PASS`. `request_revision` and `provide_evidence` return `HUMAN_ACTION_REQUIRED` with exit code 3 and no release. Any `NEEDS_REVISION`, known error, spoken-delivery or clean-copy failure, missing/corrupt evidence, stale decision, or incomplete decision remains blocked. User decisions are explicit workflow attestations; code cannot prove that the intended human authored them or that the judgment is semantically correct.
